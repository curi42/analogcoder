## T1 — `corner_render`가 전체 스윕에 도달하지 않는다 (조용히 무력한 게이트 #12)

`pvt.run_full_pvt_sweep`의 `log_event`는 기본값 `None`이고 **생산 호출부 전부가
그것을 넘기지 않는다.**

| 호출부 | 무엇 |
|---|---|
| `cli.py:505` | 진입 스윕 — 코너 씨앗의 출처 |
| `cli.py:857` | **판정 스윕** — PASS/FAIL을 정하는 그것 |
| `cli.py:460` | `verify_corners_fn`, 최적화 확인 스윕 |
| `curation.py:914`/`916` | 후보·현직 스윕 (로거가 없을 수 있음 — 없으면 범위 밖으로 두고 그 사실을 적는다) |

기록하는 곳은 `corner_sim`(중간 루프)뿐이고 그것은 `corner_reduction:`을 선언한
스펙에서만 돈다. 실측: `runs/perturb_argmax/history.jsonl`의 `corner_render`
10건이 전부 중간 루프 두 이터레이션(5테스트벤치 × 2)이고 두 스윕 사이에는 0건.

**왜 중대한가.** 이 이벤트의 존재 이유가 결함 #10이다 — `PWL` 공급 재작성이
조용히 no-op이 되어 한 테스트벤치의 전압 축이 45코너 내내 죽어 있었고 아무
기록도 없었던 사건. 그 완화책이 PASS/FAIL을 정하는 스윕에서 비어 있다.

`tests/unit/test_pvt.py:490`은 `log_event`를 **직접 넘겨서** 로깅을 증명한다 —
출하 배선이 만들지 않는 조건을 테스트가 스스로 구성한 것.

**할 일**
1. 세 `cli.py` 호출부가 `state.log_event`를 넘기게 한다.
2. `curation.py`에 로거가 있는지 확인. 없으면 범위 밖으로 두고 문서에 적는다.
3. 테스트: 진입 스윕과 판정 스윕이 각각 테스트벤치당 `corner_render`를 한 건씩
   낸다. **반증 확인 필수** — 배선을 되돌리면 그 테스트가 실패해야 한다.
4. `cli.py:460`은 최적화 확인 스윕이라 여러 번 돈다(밴드갭 실측 6회 → 30줄).
   그래도 적는다: 스텝마다 덱이 바뀌므로 렌더 상태가 실제로 달라질 수 있고,
   "코너마다 45줄"을 거부한 원래 논거는 *같은 덱의 반복*에 대한 것이었다.

## 부록 A — 교란 덱 실행 방법 (실측으로 확인된 절차)

두 스펙을 같은 교란 덱 위에서 돌린다. 스펙 차이는 `coverage:` 블록 하나뿐.

**함정 하나, 이미 한 번 밟았다.** 벤치마크를 저장소 밖으로 복사하면
`pdk_corner*.inc`가 모델을 `"../../third_party/..."` **상대 경로**로 참조해서
전부 깨진다(실측: 시뮬레이션 50건 전부 `nonzero_exit`, 씨앗 0, 두 팔 다 FAIL).
`scripts/coverage_feasibility.py`는 `resolve_includes`로 텍스트를 먼저 인라인해서
이 차이를 **보지 못한다** — 도구가 통과시킨 설정이 파이프라인에서 무너진다.

절차:
1. `benchmarks/bandgap/*.cir`, `*.inc`, 두 스펙을 작업 디렉터리로 복사
2. 복사본 `.inc` 안의 `"../../third_party/` 를 저장소 절대 경로로 치환
3. `netlist.apply_changes`로 교란 적용 (스코프는 `SUBCKT.refdes`)
4. `scripts/coverage_feasibility.py`를 **복사본 스펙**에 돌려 원본과 같은 수치가
   나오는지 확인 — 이걸 건너뛰면 무효 실행을 하나 더 만든다
5. `.venv/bin/analogcoder --spec <복사본>/spec_corner_reduction.yaml --run-dir runs/<이름>_argmax`
   그리고 `spec_corner_coverage.yaml`로 `_coverage`
