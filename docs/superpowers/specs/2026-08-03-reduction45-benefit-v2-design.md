# 45코너 코너 축소의 편익 — 재측정 사전 등록 (v2)

**이 문서는 결과가 나오기 전에 쓴다. 이후로 고치지 않는다.**

v1(`2026-08-03-reduction45-benefit-design.md`)은 **기각**으로 끝났고, 그 기각은
처치(ON) 팔이 **한 번도 관측되지 않은** 상태에서 나왔다 — 6런 중 5런이 40분 상한에
걸렸다. v1 의 결과와 결함은 `2026-08-03-reduction45-benefit-results.md` 에 있다.
**이 문서는 그 결함 넷을 고친 재측정이다.** 기능·슬롯·하니스·집계기는 그대로
쓴다(전부 리뷰를 통과했다). 바뀌는 것은 **판정 규칙과 실행 방식**이다.

## v1 의 결함 넷과, 각각을 어떻게 고쳤는가

| v1 결함 | v2 의 조치 |
|---|---|
| **1. 비용 모형이 4배 틀렸다** (실행당 15–25분으로 잡았으나 실측 반복당 ~10분) | 상한을 **런당 120분**으로. 실측 근거는 §상한 |
| **2. `void` 를 선행 조건 하나에만 걸었다** — "P 성립 + 처치 관측 0" 이 *기각*으로 흘렀다 | **선행 조건 P2 신설**: 어느 팔이든 관측 런이 0개면 `void` |
| **3. 정확성 둘째 절이 발화 불가** ("OFF 보다 적다" — P1 이 이미 `off_fail>=1` 을 보장) | **그 절을 삭제한다.** 남는 조건은 "ON 이 0건" 하나 |
| **4. 비용 지표의 "최종 스윕" 항이 구조적으로 0** (면적 단계가 직전에 같은 격자를 돌아 전량 캐시 적중) | **비용 축을 시뮬 수에서 바꾼다.** §비용 축 |

## 비용 축을 바꾼다 — 시뮬 수가 아니라 **바깥 반복 수**

v1 이 `loop_sims` 를 축으로 잡은 것은 "축소가 반복당 5 → 60 시뮬, 12배" 라는
계산에서 나왔다. **실측이 그 축을 무효화했다:** 반복 하나가 약 10분인데 그중
시뮬은 수십 초다 — **12배의 시뮬은 벽시계의 1% 안쪽**이고, 지배하는 것은 LLM
지연이다. 시뮬 수를 재는 것은 실무에서 결정적이지 않은 양을 재는 것이다.

**그래서 v2 의 비용은 "코너 확인된 판정에 이르기까지 소비한 바깥 반복 수" 다**
(재진입분을 모두 합산). 근거:

- 반복 수는 **LLM 호출 수에 비례**하고, LLM 호출이 실제 비용의 대부분이다.
- 반복 수는 **환경 독립**이다. 벽시계는 기계 부하에 따라 변하지만 반복 수는 안
  변한다. 병렬 실행을 하면서 벽시계를 판정 축으로 쓰면 경합이 판정에 들어온다.
- 축소가 실제로 비싸질 수 있는 경로가 반복 수에 잡힌다 — ON 은 더 어려운(코너)
  목표를 쫓으므로 **반복이 더 필요할 수 있다.** 그것이 이 기법의 진짜 비용이다.
- 반대로 OFF 의 실패 경로(재진입)도 반복 수로 잡힌다. 재진입은 루프 한 바퀴를
  다시 도는 것이므로 합산 반복 수가 늘어난다.

벽시계·시뮬 수·LLM 호출 수·캐시 적중은 **부수로 기록하되 판정에 쓰지 않는다.**

## 실행 방식 — **짝 단위 병렬 3파동**, 워커 고정

```
파동 1:  off_1 ∥ on_1
파동 2:  off_2 ∥ on_2
파동 3:  off_3 ∥ on_3
```

각 파동은 두 런이 **동시에** 시작하고 둘 다 끝나면 다음 파동으로 간다.

**왜 짝 단위인가.** v1 은 직렬로 `off/on` 을 교대해 "환경 드리프트가 팔과 섞이지
않게" 했다. 짝을 동시에 돌리면 두 팔이 **같은 순간의 같은 기계**를 보므로 그것이
완화가 아니라 해결이 된다.

**왜 6런 동시가 아닌가.** 코어는 10개이고 런 하나의 기본 워커는 `cpu_count-1 = 9`
다. 6런 동시는 54 워커가 되어 스윕 구간에서 심하게 경합하는데, **ON 이 시뮬을
3.6배 더 하므로 경합은 ON 을 더 때린다.** 상한은 벽시계로 재므로 그 편향은 곧장
"처치 팔이 상한에 걸린다" 로 이어진다 — v1 이 죽은 방식 그대로다.

**워커를 `ANALOGCODER_SIM_WORKERS=5` 로 고정한다.** 2런 × 5 = 10 으로 코어 수와
같다. 워커를 9→5 로 줄이면 45코너 스윕이 약 53초 → 95초가 되지만, 반복당 10분이
LLM 지연이므로 벽시계에 거의 영향이 없다. **양쪽 팔에 같은 값을 준다.**

**캐시는 오염되지 않는다.** 시뮬 캐시는 프로세스 안 메모리(`CachingBackend._entries`)
이고 디스크에 남지 않으므로, 동시 실행이 서로의 적중·불발에 영향을 주지 않는다.
각 런은 차갑게 시작한다. 이것은 v2 가 병렬을 택할 수 있는 전제이며, **확인된
사실이다**(v1 결과 문서의 배치 분석과 `simulators/cache.py`).

## 상한 — 런당 **120분**

v1 실측: 반복당 약 10분(2275/4 = 9.48분, 2400/4 = 10.0분, 2400/5 = 8.0분).
완주한 유일한 OFF 런이 **4반복 / 37.9분**이고, 잘린 OFF 런이 5반복까지 갔다.
ON 은 더 어려운 목표를 쫓으므로 그 이상이 필요할 수 있고, `on_3` 은 반복 4에서
코너 기준 통과 상태였으나 확인 스윕 전에 잘렸다.

**120분이면 반복 12회분이다.** `MAX_OUTER_ITERATIONS` 가 10 이므로 상한이 아니라
**반복 예산이 먼저 걸리는** 것이 정상 종료 경로가 된다. 상한은 병리적 실행을
막는 안전장치이지 측정을 자르는 값이 아니어야 한다.

`timeout` 은 채택 조건을 만족시키지 못하고, 아래 P2 를 통해 `void` 를 유발할 수
있다.

## 슬롯 — v1 과 동일, 하나

`benchmarks/bandgap/spec_seed_buf0_droop_45.yaml`. 45코너 기준선이 **`vbg0_droop`
단독 실패**(31.6032 @ `ss/1.62/-40`)임이 v1 태스크 1 에서 확인됐고 재확인하지
않는다. 두 팔은 그 파일의 `corner_reduction.enabled` **한 필드만** 다르며,
하니스가 계수 치환(정확히 1회)으로 파생 사본을 만든다.

**슬롯이 하나인 것은 한계다.** 결과 문서는 "이 덱·이 격자·이 씨앗에서" 라는
한정을 달아야 한다.

## 반복 — `k = 3`, 통계 검정 없음

v1 과 같다. 팔이 다르면 첫 반복부터 궤적이 갈라져 짝 탐침을 쓸 수 없고, n=3 으로
유의성을 주장하는 것은 D1 이 값을 치른 과장이다. 판정을 이산 사건에 건다.
**3 대 3 으로 갈리면 기록하고 채택하지 않는다.**

## 판정 규칙 — 결과를 보기 전에 고정

**선행 조건을 둘 다 먼저 본다. 하나라도 불성립이면 `void` 이고 채택 규칙을
적용하지 않는다.**

- **P1 (사건이 발생했는가):** 축소를 **끈** 팔의 관측 런 중 **중간 루프가 PASS 로
  나온 뒤 최종 스윕이 실패한 실행이 1건 이상**. v1 에서 실증됐다(`off_3`).
- **P2 (측정이 가능했는가 — v2 신설):** **두 팔 모두 관측 런이 1건 이상.**
  "관측" := 상한에 걸리지 않았고 `result.json` 과 `history.jsonl` 을 남겼다.
  어느 팔이든 0건이면 **`void`** 다. v1 이 이 조항을 갖지 못해, 처치 팔을 한 번도
  못 본 상태가 *기각*이라는 라벨로 나갔다.

둘 다 성립하면:

- **채택** := ON 이 아래 둘을 **모두** 만족한다.
  1. **정확성**: ON 의 관측 런에서 "중간 PASS 인데 최종 스윕 실패" 가 **0건**.
  2. **비용**: ON 의 **총 바깥 반복 수 중앙값**이 OFF 의 **1.5배 이하**.
- **기각** := 위를 만족하지 못한다. 동률·부분 성립은 기각이다.

**1.5배의 근거.** OFF 의 실패 경로인 재진입은 루프 한 바퀴를 다시 도는 것이므로
합산 반복이 최소 1 늘고 전체 스윕이 한 번 더 붙는다. v1 관측에서 OFF 는 4–5
반복을 썼으므로 재진입 한 번은 대략 +25~50% 다. ON 이 그 범위 안의 추가 반복으로
**틀린 PASS 를 0건**으로 만든다면 값을 한 것이다. 잡음이 아니라 **의미**에서 온
값이다(반복 수는 정확히 세진다).

**발화 가능성 확인(v1 결함 3 의 재발 방지).** 두 절 각각에 거절 가능한 입력이
존재한다: 정확성은 ON 에서 사건이 1건이라도 나면 거절하고, 비용은 ON 중앙값이
OFF 의 1.5배를 넘으면 거절한다. 두 조건은 서로를 함의하지 않는다.

## 부수적으로 기록하되 판정에 쓰지 않는다

벽시계, 시뮬 수(`loop_sims`/`area_phase_sims`), LLM 호출 수, 캐시 적중·불발,
재진입 횟수, `corner_seed` 의 `dropped`, 탐침 승격 코너 수, 착지 덱의 SHA-256,
그리고 각 런의 `vbg0_droop` 궤적. **판정에 쓰면 규칙이 둘이 된다.**

`area_optimization` 의 `status`/`steps_accepted`/`corner_confirmed`/착지 버전은
**관측된 모든 런에 대해** 결과 문서가 적는다 — v1 이 이 확인을 요구해 놓고
이행하지 않았고, 전체 브랜치 검토가 그것을 잡았다.

## 비용

파동당 최대 2시간, 3파동 = **최대 6시간**. 거의 무인이다.

## 이 측정이 답하지 못하는 것 — 미리 적는다

- **덱 하나 · 격자 하나 · 씨앗 하나 · `k=3` · 검정 없음.** 일반성 주장 불가.
- **탐침의 기여를 분리하지 못한다.** ON 은 씨앗과 탐침을 함께 켠다.
- **`coverage:` 체제는 대상이 아니다.** 2026-07-30 에 자기 규칙으로 기각됐다.
- **벽시계로의 이득은 판정하지 않는다.** 비용 축을 반복 수로 잡았으므로, "실제로
  몇 분 빨라지는가" 는 이 측정의 답이 아니다.
- **v1 의 관측 1건(`off_3` 의 2.08배)이 얼마나 자주 일어나는지**는 여전히 빈도
  추정이 아니다. v2 가 OFF 3런을 관측하면 3건 중 몇 건인지는 알 수 있으나, 그것도
  n=3 이다.

## 격자를 넓히지 않는다. 슬롯을 골라내지 않는다. 임계값을 결과 뒤에 고치지 않는다.
