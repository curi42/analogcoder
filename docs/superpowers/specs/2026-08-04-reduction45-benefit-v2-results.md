## 기법이 사는 것 — `vbg0_droop` 궤적이 그것을 그대로 보여준다

중간 루프가 매 판정에서 본 `vbg0_droop` 값:

```
off_1  19.932 → 18.911 → 17.786 → 16.197 → 15.506 → 14.815   (PASS 선언)
off_2  19.932 → 18.911 → 12.505                              (PASS 선언)
on_1   31.603 → 28.108 → 27.127 → 23.085 → 19.018 → 14.920   (PASS 선언)
on_2   31.603 → 26.181 → 23.021 → 32.152 → 58.849 → 16.638 → 13.672
```

**OFF 는 19.932 에서 출발한다. ON 은 31.603 에서 출발한다.** 같은 덱, 같은 순간이다 —
19.932 는 명목 한 점이고 31.603 은 45코너의 진짜 최악값이다(`ss/1.62/-40`). OFF 의
튜너는 **1.59배 낙관적인 숫자를 상대로 최적화**하고, 그 숫자가 15 아래로 내려가는
순간 PASS 를 선언한다. 최종 스윕이 그것을 22.94 / 20.14 로 뒤집는다.

v1 이 단 한 번(`off_3`, 명목 12.5891 대 코너 26.2401 = 2.08배) 관측한 실패가
**2/2 로 재현됐다.** 존재 증명이 아니라 이 슬롯에서의 재현이다 — 여전히 빈도 추정은
아니다(n=2).

`on_2` 의 32.152 → 58.849 는 튜너가 반복 4~5 에서 잘못된 방향으로 크게 움직였다가
되돌아온 흔적이다. 축소가 켜져 있으면 그 악화가 **즉시 보인다**; 꺼져 있으면 명목이
가리고 지나간다.

## 비용 절 — 기각의 근거, 그리고 그 절의 여섯 번째 결함

규칙이 요구한 값: ON 의 총 바깥 반복 중앙값 ÷ OFF 의 그것 ≤ 1.5.

- 파동 3 포함: OFF `[5, 2, 0]` → 중앙값 **2**, ON `[5, 6, 0]` → **5**, 비 **2.5**.
- 파동 3 제외: OFF `[5, 2]` → **3.5**, ON `[5, 6]` → **5.5**, 비 **1.571**.

**두 읽기 모두 1.5 를 넘으므로 기각이다.** 백엔드 실패를 어떻게 다루든 판정이 움직이지
않는다는 것이 이번의 다행이다 — 아래 다섯 번째 결함이 결정적이지 않았다는 뜻이다.

**그러나 이 절의 유도 근거는 코드에 의해 반증된다 — 여섯 번째 사전 등록 결함.**
v2 설계는 비용 축을 반복 수로 고르며 이렇게 적었다:

> "반대로 OFF 의 실패 경로(재진입)도 반복 수로 잡힌다. 재진입은 루프 한 바퀴를 다시
> 도는 것이므로 합산 반복 수가 늘어난다."

**거짓이다.** `cli.py:727` 이 `retry_budget = reduction.retry_budget if
reduction_active else 0` 이고 `cli.py:1024` 가 `if not reduction_active or attempt >=
retry_budget: break` 이므로, **재진입은 ON 팔에서만 가능하다.** OFF 는 최종 스윕이
깨지면 그대로 FAIL 로 끝나고 복구에 한 반복도 쓰지 않는다. 실제로 네 관측 런 모두
`reentry_count = 0` 이다.

그러므로 이 비용 지표가 실제로 비교한 것은

> **"틀린 답에 도달하는 데 든 반복 수" 대 "맞는 답에 도달하는 데 든 반복 수"**

이다. `off_2` 는 2 반복 만에 멈췄는데, 그것은 싸서가 아니라 **일찍 틀렸기 때문**이다.
같은 축에서 `on_2` 는 6 반복을 쓰고 코너에서 통과하는 덱을 냈다. 두 수를 나눈 비는
"효율"이라는 이름을 붙일 수 있는 양이 아니다.

**그럼에도 규칙은 문자 그대로 적용했다.** 결과를 보고 지표를 고치는 것은 이 저장소가
D1 에서 값을 치르고 금지한 행위다. 이 결함은 **다음 사전 등록이 고쳐야 할 입력**이지
이번 판정을 바꾸는 근거가 아니다.

**판정이 반복 하나에 걸려 있다는 것도 함께 적는다.** n=2 이므로 중앙값은 두 정수의
평균이다. ON 이 어느 한 런에서 반복을 하나만 덜 썼다면 — `[4, 6]` 또는 `[5, 5]` —
중앙값 5.0, 비 **1.4286** 으로 **채택**이었다. 임계값 1.5 와 관측값 1.571 의 간격은
5% 이고, 반복 수의 눈금은 1 이다. **이 축은 n=2 에서 판정을 지탱하지 못한다.**

## 다섯 번째 사전 등록 결함 — 이번엔 결정적이지 않았다

v2 설계의 "관측" 정의는 **"상한에 걸리지 않았고 `result.json` 과 `history.jsonl` 을
남겼다"** 이다. 파동 3 의 두 런은 이 정의를 **문자 그대로 만족한다** — 상한에 걸리지
않았고(69초), 두 파일 다 남겼다. 그러나 바깥 반복은 0회였다.

첫 시도(집계 전 폐기, `runs/reduction45_backend_failure/`)에서는 이 결함이 결정적일
뻔했다: 깨진 런들을 포함하면 채택, 제외하면 n=1 로 채택 불가였다. 이번에는 두 읽기가
모두 기각이므로 결함이 판정을 움직이지 않았다. **다음 사전 등록은 "관측"에 진행
증거를 요구해야 한다** — 예: `orchestration_attempt.iterations_used >= 1`.

**계측 구멍도 하나 있었고 고쳤다.** 하니스가 런별 `stdout`/`stderr` 를 갈라 저장하지
않아 첫 시도에서는 실패를 런에 귀속시킬 수 없었다. 고친 뒤 알게 된 사실:
`RuntimeError: aclose(): asynchronous generator is already running` 는 **완주한
`on_2`(99.8분, PASS)의 stderr 에도 똑같이 있다.** 종료 시 asyncgen 정리 경고이지
실패 신호가 아니다. **판별자는 stderr 가 아니라 `orchestration_attempt.failure_reason`
이다** — 이미 `history.jsonl` 에 실려 있었고, 첫 시도에서 "오류 이벤트가 없다"고 적은
것은 틀렸다.

## 부수 기록 — 판정에 쓰지 않는다

- **씨앗**: 두 ON 런 모두 `mode=argmax`, `seed_size=9`, `points_per_tb=11`,
  `covered 22/22`, `dropped=[]`. 반복당 **55 시뮬** (11 × 5 테스트벤치).
  CLAUDE.md 가 `spec_corner_reduction_45.yaml` 에서 기록한 10 / 12 / 60 과 다른 것은
  이 슬롯의 `vbg0_droop` 임계값이 다르기 때문이며 모순이 아니다.
- **탐침 승격**: `on_1` 6개, `on_2` 8개. 최종 집합은 각각 덱+15, 덱+17.
- **재진입**: 네 런 모두 0. ON 은 최종 스윕이 통과해서, OFF 는 재진입이 불가능해서다.
- **argmax 드리프트**: 진입↔판정 스윕 사이 이동한 기준이 `off_1` 1, `off_2` 1,
  `on_1` 3, `on_2` 4개. 22개 전부 `compared`, 측정 불가 0.
- **캐시**: `off_1` 250적중/480불발, `on_1` 730/2745, `off_2` 235/465,
  `on_2` 829/2909.
- **면적 단계의 비대칭이 벽시계를 오염시킨다.** OFF 두 런은 `UNCHANGED 0수락/0거절`
  (코너에서 깨지는 덱이라 `accept_step` 이 아무것도 수락할 수 없다). ON 두 런은
  14/6 과 16/4 를 수락하고 확인 스윕까지 돌았다. 즉 ON 의 90–100분 중 상당 부분은
  **OFF 가 아예 하지 않는 일**이다. 벽시계를 비용 축으로 쓰지 않기로 한 결정이
  결과적으로 옳았다.
- **착지 덱 SHA-256**: `off_1` `4e41e68b5b9a…`, `on_1` `50cbf0994261…`,
  `off_2` `877264ff4b30…`, `on_2` `13c40d147829…`.

## 이 측정이 말하지 못하는 것

- **덱 하나 · 격자 하나 · 씨앗 하나 · 팔당 관측 2회 · 통계 검정 없음.** 일반성 주장 불가.
- **탐침과 씨앗의 기여가 분리되지 않는다.** ON 은 둘을 함께 켠다.
- **비용은 판정되지 않은 것으로 읽어야 한다.** 지표의 유도 근거가 반증됐으므로,
  "축소가 1.5배 안에 들지 못했다"는 사실이고 "축소가 비싸다"는 이 측정의 결론이 아니다.
- **정확성 절의 성립은 2/2 이지 0/N 이 아니다.** ON 이 틀린 PASS 를 내지 않는다는
  주장의 근거는 관측 2회뿐이다.

## 다음 사전 등록이 고쳐야 할 것 — 여섯 결함의 누계

1. (v1) 비용 모형이 4배 틀렸다 → v2 가 상한 120분으로 고침.
2. (v1) `void` 가 선행 조건 하나에만 걸렸다 → v2 가 P2 신설로 고침.
3. (v1) 정확성 둘째 절이 발화 불가 → v2 가 삭제로 고침.
4. (v1) 비용 지표의 "최종 스윕" 항이 구조적으로 0 → v2 가 축을 반복 수로 바꿔 고침.
5. (v2) **"관측"의 정의가 백엔드 실패를 배제하지 못한다.** 이번엔 비결정적.
   → 진행 증거(`iterations_used >= 1`)를 요구할 것.
6. (v2) **비용 절의 유도 근거가 거짓이다** — OFF 는 재진입할 수 없으므로 실패 경로의
   비용을 지불하지 않는다. → 두 팔을 **같은 종착점**(코너 확인된 PASS)까지 몰고 가서
   재는 지표를 쓰거나, 비용 절을 아예 두지 말 것.

**결함 5와 6은 둘 다 "이 규칙의 어느 항이 어떤 입력에서 어떤 값을 낼 수 있는가"를
사전에 다 따지지 않아 생겼다.** 서 있는 질문 2와 같은 모양이고, 이 프로젝트에서
반복되는 실패다. 다음 사전 등록은 **각 절과 각 항에 대해 비자명한 값을 낼 수 있는
입력을 하나씩 적시**하고 시작해야 한다.
